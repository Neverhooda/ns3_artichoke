# Восстановление маршрутов в PLC-подобной сети счётчиков

Эксперимент на ns-3.26. Сеть счётчиков электроэнергии передаёт показания на концентратор по многоскачковой маршрутизации AODV. Один счётчик внезапно выпадает из сети. Вопрос: сколько времени остальные счётчики, чей маршрут шёл через него, остаются без связи, и почему именно столько.

## Модель

### Топология: кольцевой фидер

```
              11 10  9  8  7
          12                  6
        13                      5
        14                      4   <- путь к концентратору идёт через 3
        15                      3   <- выпадает в t = 30 с
        16                      2
          17                  1
              18 19 ... 23  0   <- концентратор
```

- 24 узла стоят по окружности (`--size`). Узел 0 — концентратор, остальные счётчики.
- Соседние узлы разделяет 100 м «кабеля» (`--step`). Радиус слышимости около 150 м, поэтому каждый узел слышит только двух ближайших соседей. Сигнал до концентратора идёт цепочкой через промежуточные счётчики, как в PLC-сети, где сигнал затухает вдоль линии и ретранслируется модемами.
- Кольцо выбрано специально: после отказа узла 3 счётчики 4…11 могут достучаться до концентратора только в обход, по длинной стороне кольца (до 20 скачков).

### Канал

Это **не** физическая модель PLC. Используется Wi-Fi 802.11b ad-hoc на 1 Мбит/с с моделью затухания по умолчанию (`LogDistance`). От PLC взяты:

- линейная топология с ретрансляцией через соседей;
- общая среда: соседи мешают друг другу (CSMA/CA);
- низкая скорость по меркам Wi-Fi.

Нас интересует поведение протокола маршрутизации, и для этого такого приближения достаточно. Чего в модели нет: импульсных помех, частотно- зависимого затухания, асимметрии каналов. Это хорошие направления для доработки.

### Трафик

Каждый счётчик раз в `--interval` секунд (по умолчанию 1 с) отправляет показание 64 байта по UDP на концентратор. Старт сдвинут случайно в пределах одного интервала, чтобы счётчики не передавали синхронно. Первые 15 с (`--warmup`) сеть строит маршруты, данных нет.

### Отказ

В момент `--failAt` (30 с) узел `--failNode` (3) переносится далеко за пределы слышимости. Для остальных это выглядит как внезапное пропадание соседа: модем выключили, линию оборвали.

### Маршрутизация

AODV из ns-3.26 с параметрами по умолчанию, HELLO включены (`--hello`). Любой атрибут AODV можно поменять из командной строки, например:

```
--ns3::aodv::RoutingProtocol::RreqRetries=1
```

Внимание: часть параметров AODV в ns-3 вычисляется **один раз в конструкторе** из других (`NetTraversalTime = 2 * NodeTraversalTime * NetDiameter`, `PathDiscoveryTime = 2 * NetTraversalTime`, …). Если поменять только `NetDiameter`, производные значения останутся старыми.

## Что измеряется

Концентратор запоминает время прихода каждого показания. После отказа для каждого счётчика находится самая длинная пауза между соседними показаниями.

- В норме пауза равна интервалу (1 с).
- Счётчик считается «отрезанным», если пауза больше `1.5 × interval + 0.2` с.
- Время восстановления счётчика — момент первого показания после этой паузы минус момент отказа.

Сценарий может записать:

| Опция | Что в файле |
|---|---|
| `--csv=FILE` | одна строка на прогон: сколько счётчиков отрезано, медиана и максимум восстановления, число служебных пакетов AODV |
| `--meterCsv=FILE` | по строке на счётчик: отправлено, получено, самая длинная пауза, время восстановления |
| `--timelineCsv=FILE` | по строке на секунду: сколько счётчиков концентратор услышал |
| `--traceCsv=FILE` | каждый служебный пакет AODV (кроме HELLO): время, узел, тип RREQ/RREP/RERR, TTL, адресат поиска, инициатор, число скачков |

Трасса — главный инструмент. Сборка ns-3 в образе оптимизированная, и `NS_LOG` в ней не работает.

## Запуск

Нужен Docker. Из корня репозитория:

```bash
docker build -t artichoke-ns3:3.26 docker
docker run --rm -it -v "$PWD/plc:/opt/ns-allinone-3.26/ns-3.26/scratch/plc" \
  -w /opt/ns-allinone-3.26/ns-3.26 artichoke-ns3:3.26 bash

./waf --run plc
./waf --run "plc --traceCsv=/tmp/trace.csv --meterCsv=/tmp/meters.csv"
```

Пример вывода:

```
config=baseline ring=24 step=100 run=1 failNode=3
meters cut off:           11
never recovered:          0
recovery median / max:    10.7543 / 11.1439 s
AODV control packets:     2695
```

`--run=N` меняет зерно генератора. Для выводов делайте несколько прогонов.
